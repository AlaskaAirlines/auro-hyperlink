# AB#1639236

## Executive Summary

Engineers building with the Auro hyperlink component get help from their code editor — hover descriptions, autocomplete, and warnings on unsupported values. For the two settings controlling a button-style link's shape and size, the editor knew the settings existed but had nothing to say about them: no explanation, no list of valid values, no way to flag a typo. A retired dark-background setting wasn't marked as outdated, so engineers could keep using it without learning of its replacement.

This work filled in that missing information. While doing so, we found the retired setting had been declared twice under two slightly different names. The duplicate was invisible in the documentation but was quietly holding the component together: one copy carried the behavior that made the setting work from JavaScript, and the other — the documented one — did not. We consolidated onto the documented name and fixed a pre-existing defect where it silently did nothing when set that way.

Two review rounds corrected the approach. The first caught that deleting the undocumented name outright would be a breaking change shipped as a patch: it appeared in the published package's type definitions even though it was absent from this component's docs. It was restored as a deprecated alias. The second caught that the restored alias stopped working for frameworks that set the value *before* the component finishes loading — the exact case the alias exists to serve — which a short addition to the component's setup now handles, covered by tests verified to fail without it.

Ticket: [AB#1639236](https://itsals.visualstudio.com/E_Retain_Content/_workitems/edit/1639236)

## The Problem

The `shape` and `size` appearance settings for the button-style hyperlink shipped with no description and no list of valid values, recorded only as accepting "some text." Editors could complete the attribute names but couldn't say what they did, suggest values, or warn on a typo. A retired dark-background option was described as outdated only in prose, which editors can't act on, so it never rendered struck through. The component's automated documentation check was reporting six warnings about these gaps, which is how they were identified.

## Root Cause

Two independent causes.

**Missing manifest metadata.** In `src/layoutElement/auroElement.js`, `shape` and `size` were declared as Lit reactive properties with no JSDoc. The manifest generator derives existence, attribute name, and reflection from the Lit declaration, but *descriptions* and *narrowed types* from JSDoc. So both properties were published — 8.0.5's `custom-elements.json` lists each with `"type": {"text": "string"}` and `reflects: true` — but with no description and a useless-but-true `string` type. They were *published but undescribed*, not absent.

`docs/api.md` showed neither, because its renderer drops members carrying no description — the same filter that hid `onDark`.

Separately, `ondark` in `src/component-base.mjs` had a human-readable `DEPRECATED - use appearance="inverse" instead.` description but no machine-readable `@deprecated` tag.

**A shadowed duplicate property.** The same `ondark` HTML attribute was claimed by two Lit reactive properties:

- `ComponentBase.ondark` — `{ type: Boolean }`, no `reflect`
- `AuroElement.onDark` — `{ type: Boolean, attribute: "ondark", reflect: true }`

Lit merges `elementProperties` superclass-first, so the subclass registered second and won the attribute→property map: the attribute drove `this.ondark`, and `onDark` never received it. But reflection is configured per-property, and only `onDark` set `reflect: true`. That split the behavior in half:

| Usage | `ondark` attribute set? | Dark styling applied? |
| --- | --- | --- |
| `<auro-hyperlink ondark>` | yes | yes |
| `el.ondark = true` | **no** | **no** |
| `el.onDark = true` | yes | yes |

All dark styling is attribute-driven (`src/styles/color.scss` selects on `:host([ondark])` variants; the `hyperlink--ondark` class in `getMarkup()` has no matching rules and is inert). So `onDark` — published, but absent from `docs/api.md` and unknown to anyone reading the repo's docs — was the only working JavaScript path to the styling, while the documented `ondark` silently did nothing.

Adding `@deprecated` to both declarations is what made `onDark` appear in `docs/api.md` for the first time, surfacing the collision as two rows for one feature.

## The Fix

Cumulative change from merge-base `97f9a7f`:

**`src/layoutElement/auroElement.js`**

- Added JSDoc descriptions and `@type` string-literal unions to `shape` (`'rounded' | 'pill' | 'circle' | 'square'`) and `size` (`'xs' | 'sm' | 'md' | 'lg' | 'xl'`).
- Removed the `onDark` *reactive property* declaration, so it no longer claims the `ondark` attribute.

**`src/component-base.mjs`**

- Added `reflect: true` to `ondark`, relocating the behavior `onDark` had provided onto the documented property.
- Re-added `onDark` as a plain `get`/`set` pair delegating to `this.ondark`. Not reactive, declares no attribute, so the collision cannot recur.
- Added `_rescuePreUpgradeOnDark()`, called from the constructor after `_initializeDefaults()` — see Why This Works.
- Gave both `@deprecated` tags a message (`Use \`appearance="inverse"\` instead.`) and dropped the now-redundant `DEPRECATED - ` prefix from the descriptions. A bare `@deprecated` makes the analyzer emit the *string* `"true"`, and the typegen concatenates tag value with description, so consumers were hovering `@deprecated true - DEPRECATED - use ...`.
- Removed the `@private` JSDoc from the `shape`/`size` assignments in `_initializeDefaults()`, which contradicted their new public descriptions. Privacy is driven by `@forcePrivate {'layout'}` in `src/auro-hyperlink.js:28`, so the manifest is unchanged — verified by regeneration.

**`test/auro-hyperlink.test.js`** — 12 new tests: 3 on the `ondark` attribute/property/reflection paths (previously zero coverage), 3 on the `onDark` alias for upgraded elements, 4 pre-upgrade (each asserting `el.updateComplete === undefined` before assigning, then calling `register(tagName)`), and 2 end-to-end asserting `type="cta"` propagates `appearance="inverse"` to the inner button via both names.

**`docs/api.md`** — regenerated. `shape` and `size` appear for the first time; `onDark` appears with no attribute value (property only). This renderer never consults the `deprecated` field — no strikethrough, no deprecated column — which is why both descriptions still carry the word "Deprecated" in prose. The machine-readable tag is what serves editors.

**`package.json`** — `@aurodesignsystem/auro-cli` `^3.7.1` → `^4.0.0`, whose `cem-check` surfaced the six warnings.

## Why This Works

A single reactive property owns the `ondark` attribute and both receives and reflects it, so the attribute and property cannot disagree. The `onDark` accessor sits above that owner rather than beside it: it holds no state and cannot drift, because it *is* `ondark`. Moving `reflect: true` onto `ondark` rather than simply deleting `onDark` is what makes this safe — deleting the duplicate alone would have removed the only working property→attribute path.

Net consumer capability is a strict superset of 8.0.5:

| Usage | 8.0.5 | After this change |
| --- | --- | --- |
| `el.onDark = true` | attribute set, styling applied | same |
| `el.onDark` after `<auro-hyperlink ondark>` | `undefined` — attribute never reached it | `true` |
| `el.ondark = true` | **silently no-op** | attribute set, styling applied |

The one changed reading is `el.onDark` as a getter, which previously returned `undefined` regardless of state. Returning the real value is a fix, not a withdrawal.

At the manifest level, `onDark` moves from a field with `attribute: "ondark"` and `reflects: true` to a field with neither — matching how the generator already describes other accessor-backed members (`role`, `safeUri`). This is the manifest becoming accurate, and it's inert for consumers: the `ondark` attribute is still declared, parsed, and reflected, just by `ondark`. A CEM-driven wrapper generator emits `onDark` as a property binding instead of an attribute binding, which produces the same runtime result because the property reflects.

**The alias needed a pre-upgrade rescue to actually be equivalent.** Demoting `onDark` to a plain accessor silently dropped a capability that came free with the reactive declaration. Lit's `__saveInstanceProperties()` rescues values assigned before upgrade, but only for names in `elementProperties` — a plain accessor is not in that map:

```js
const el = document.createElement("auro-hyperlink"); // definition not yet loaded
el.onDark = true;                                    // own DATA property — no setter exists yet
document.body.appendChild(el);
// ...definition loads, element upgrades...
```

After upgrade, that own data property shadows the prototype accessor permanently. Measured: `el.ondark` stayed `false`, no attribute appeared, no styling applied — and a subsequent `el.ondark = false` left `el.onDark` reading `true`, a desync with no way back. Assigning `el.ondark` pre-upgrade worked fine, because Lit rescues that one.

This is what React, Angular, and Vue do when setting properties on a lazily-loaded custom element — precisely the population a compatibility alias exists to serve. 8.0.5 handled it, because `onDark` was reactive with `reflect: true`. The shim added to prevent one regression had introduced a different one.

`_rescuePreUpgradeOnDark()` closes it: if an own `onDark` property exists, it is deleted and re-assigned so it routes through the setter. Order matters — it must run *after* `_initializeDefaults()` sets `ondark = false`, or the default would clobber the rescued value.

`onDark` is unused inside this repo — every internal read is `this.ondark` (`src/auro-hyperlink.js:121,160`) or an `[ondark]` selector — so the alias adds no internal coupling to unwind at removal time.

Union values were confirmed against `node_modules/@aurodesignsystem/auro-button/custom-elements.json` rather than assumed: exact match on both.

**The `shape`/`size` narrowing does not reach TypeScript consumers at all.** The obvious reading is that narrowing `string` → union tightens the compile surface. It doesn't, because `dist/index.d.ts` opens with two **bare** specifiers:

```ts
import type { AuroHyperlink } from "src/auro-hyperlink.js";
import type { AuroElement } from "src/layoutElement/auroElement.js";
```

Non-relative, so TypeScript resolves them as package names out of `node_modules` — and `src/` is in neither the tarball nor `package.json`'s `files` array. Every declaration is an indexed access into that missing type (`shape?: AuroHyperlink["shape"]`), so all of them degrade to `any`. Measured against a synthetic install of the built `dist/` (strict, `skipLibCheck: false`):

| Probe | Result |
| --- | --- |
| `index.d.ts:1` and `:2` | `TS2307: Cannot find module 'src/auro-hyperlink.js'` |
| `{ shape: someString }` where `someString: string` | **no error** — the prop type is `any` |
| `{ totallyBogusKey: true }` | `TS2353: does not exist in type 'AuroHyperlinkProps'` |

So the props type enforces **key existence** but not **member value types**. `string → union` is `any → any` downstream, in both versions — nothing for a release note to warn about, and no consumer code that compiled before will stop compiling. This removes the last argument against treating the change as a PATCH.

It does **not** weaken the finding that deleting `onDark` was breaking. Key existence is the half still enforced: `{ onDark: true }` compiles and `{ totallyBogusKey: true }` does not, so removing the key would have broken TS consumers exactly as described.

The broken `.d.ts` is a real defect and **out of scope here** — it comes from the shared typegen in `@aurodesignsystem/auro-cli` and affects every member of every Auro component's props type. Fixing it inside this ticket would turn an inert narrowing into a live one and change the release's compatibility story. Logged as follow-up.

**Verification**

- `npx auro cem-check` — *"CEM contract clean — no violations."*
- `npx auro test` — **49 passed, 0 failed** (37 before). The `auro-hyperlink-button scheduled an update` Lit dev-mode warning was confirmed present pre-change and is unrelated.
- **Regression tests confirmed to fail without the fix.** With only the `_rescuePreUpgradeOnDark()` call commented out: **47 passed, 2 failed** — `applies an onDark value assigned before upgrade` and `keeps onDark and ondark in sync after a pre-upgrade assignment`. The two control tests pass on both trees, establishing the failure is specific to the accessor and not the harness.
- `npm pack @aurodesignsystem/auro-hyperlink@8.0.5` and a field-level manifest diff: **19 public fields each side, zero removed, zero added.** `_rescuePreUpgradeOnDark` is emitted as `privacy: "private"` and a method, so it stays out of the public surface. Exactly four fields differ, all intended: `ondark` gains `deprecated` + `reflects`; `onDark` gains `deprecated`/`description` and drops `attribute`/`reflects`/`privacy`; `shape` and `size` gain descriptions and narrowed types.
- `npx biome check` diffed before and after: identical. All 10 findings pre-existing, none in added lines.

## Outcome

Engineers now get full editor support for both appearance settings: a hover description, autocomplete limited to accepted values, and a warning on typos. The retired dark-background option is marked outdated wherever the editor supports showing it. The automated documentation check passes cleanly.

Beyond the documentation work, a latent defect was found and fixed: the dark-background option now works when set from JavaScript, where previously it was silently ignored — covered by tests for the first time.

Nothing available in the last published release was taken away. The alternate name still works, including when set before the component finishes loading, and now carries the deprecation marking. Upgrading is a no-op; removal will land in a deliberate major.

The editor-validation benefit is currently realized only where tooling reads `custom-elements.json` — VS Code HTML custom-data, and manifest-driven framework wrappers. TypeScript and JSX consumers get it once the packaging defect in `dist/index.d.ts` is fixed separately, with no further change needed here.

**Resolved**

- **Retired options flagged as deprecated so generated types render them struck through** — `@deprecated` added to `ondark` and to the `onDark` alias, each carrying `Use \`appearance="inverse"\` instead.` as its message. The ticket described "a couple of retired options"; there is one retired *feature* under two names, and both are marked.
- **Both appearance options carry a hover description** — JSDoc added for `shape` and `size`; both render in `docs/api.md` for the first time.

- **Union values verified against auro-button's actual supported values** — exact match on both.
- **CEM contract passes with 0 errors and 0 warnings** — the six warnings are resolved.

Adding `reflect: true` to `ondark` is a deliberate runtime behavior change: `el.ondark = true` now applies dark styling where it previously did nothing. The ticket assumed a pure metadata change; completing the metadata exposed a latent defect that had to be fixed to avoid shipping a regression. The change is additive and tested, but the ticket's "Breaking change: None — no runtime behavior change" framing is no longer strictly accurate, and the release carries a fix rather than only documentation.

## Learnings

- **Writing a description is what makes a property visible to review.** `shape`, `size`, and `onDark` were all published in `custom-elements.json` and `dist/index.d.ts` and all invisible in `docs/api.md`, because that renderer drops members without a description. Adding descriptions didn't add them to the API; it added them to the *committed view* of the API — which is what made the collision legible as two rows for one feature. Undescribed members are shipped-but-unreviewable.
- **The published tarball is the API contract, not the repo.** The judgment that deleting `onDark` was safe rested entirely on the working tree: absent from `docs/api.md`, unread in `src/`. Both true, both beside the point. Every artifact that reaches consumers is generated and gitignored (`dist/` at `.gitignore:18`, `custom-elements.json` at `:28`), and the one generated artifact that *is* committed is the most filtered of the three. `npm pack <pkg>@<last-version>` and read what shipped.
- **Read the generated artifact, not just the manifest it came from.** `custom-elements.json` looked correct at every stage. Both remaining defects were only visible one step downstream in `dist/index.d.ts` — the `@deprecated true` concatenation, and the unresolvable `src/` imports that make every value type `any`.
- **In Lit, attribute ownership and reflection are independent.** Superclass/subclass merging decides which property receives an attribute (subclass wins, registered last), but `reflect` is per-property. Two properties can share one attribute with one reading it and the other writing it — a split no single file makes visible.
- **"Zero reads" does not mean dead code.** A grep showing no reads of `onDark` looked like proof it was inert. Its `reflect: true` was a live side effect. A short throwaway test measuring actual attribute/property state settled in one run what static reading had gotten wrong.
- **A plain accessor is not a drop-in replacement for a reactive property.** Demoting `onDark` consciously gave up attribute ownership — that was the point — but also unknowingly gave up Lit's pre-upgrade rescue, producing a *different* silent regression in the same feature, introduced by the fix for the first one. When replacing a framework-managed declaration with hand-written code, enumerate what the framework was doing for you, not just the behavior you were targeting.
- **Test the state the bug lives in, not the state the harness makes convenient.** All six tests added in the first pass used `fixture()`, which returns an already-upgraded element — the one condition under which the shadowing bug cannot occur. Green, specific, and structurally incapable of catching the regression. A genuine pre-upgrade element takes three lines (`createElement` on an undefined tag, assign, then `register`). And confirm the regression test fails without the fix: without that step, a test passing for the wrong reason is indistinguishable from one that guards the behavior.
- **A bare `@deprecated` is worse than it looks.** It satisfies "is this member flagged deprecated" everywhere that question is asked — manifest field present, editor strikethrough, `cem-check` passing — while the typegen ships `@deprecated true - DEPRECATED - use …` to every consumer's hover card. `cem-check` has a `deprecated-no-detail` rule for exactly this, but it tests `deprecated === true` and the analyzer emits the *string* `"true"`, so it never fired.
- **A commit-type prefix is a compatibility claim, not just a changelog label.** `fix:` cuts a PATCH, asserting consumers can upgrade without action; removing a published member contradicts that no matter how the body is worded. Separately, check what the prefix does to the release before choosing it on accuracy alone — `docs:` sounded accurate for metadata work, but this repo's shared config (`@aurodesignsystem/auro-config/releaserc`) only grants a release to `docs` scoped `README`, so an unscoped `docs:` would have meant the improved types never reached consumers.
- **A "no runtime behavior change" ticket can stop being one.** Re-validate that framing at the end of the work rather than carrying the original assumption into the PR description and release notes.
- **`_initializeDefaults()` cannot read `this.type`.** It runs from the constructor (`src/component-base.mjs:18`), before attributes are applied, so `this.type === "cta"` is always false there. Any defaulting conditional on `type` belongs in `willUpdate`/`connectedCallback`. The `layout`, `shape`, and `size` assignments still carry this dead conditional — pre-existing and left outside this change's scope.
- **`src/layoutElement/auroElement.js` is duplicated in spirit across sibling components.** Fixes here don't propagate, so siblings may carry the same collision. `auro-button@12.4.0` still publishes both `onDark` and `ondark`; this change keeps auro-hyperlink aligned with that surface rather than diverging ahead of a coordinated major.

## Iterations That Didn't Work

- **Deleting `onDark` on its own.** A repo-wide grep finding zero reads suggested dead code. An empirical probe showed otherwise: `onDark` held the only `reflect: true`, so removing it alone would have left `el.ondark = true` with no path to the `:host([ondark])` styling. Replaced by removing `onDark` *and* moving `reflect: true` onto `ondark`.
- **Removing `onDark` from the public API at all, in a `fix:` commit.** Even after the reflection behavior was safely relocated, deleting the name was still wrong — and it shipped in the first iteration of this branch before review caught it. The failure was scoping every check to the working tree. `onDark` was genuinely absent from `docs/api.md`, which read as proof it had never been published. It wasn't: `dist/index.d.ts` declared `"onDark"?: AuroHyperlink['onDark']`, and 8.0.5's `custom-elements.json` listed it as a public field with `attribute: "ondark"` and `reflects: true`. Both generated and gitignored, so neither was opened. Merging would have broken TS/JSX compilation for any consumer referencing it, turned `el.onDark = true` into a silent expando in plain JS, and diverged from `auro-button@12.4.0` — all under a PATCH with no `BREAKING CHANGE:` footer. Two exits existed: re-cut as a major, or restore as a deprecated alias and remove in a deliberate major later. The alias was chosen. It was described at the time as costing two lines; it cost six.
- **Restoring `onDark` as a bare accessor, with no pre-upgrade rescue.** Written on the reasoning that a stateless delegation cannot diverge from what it delegates to — true after upgrade, false before it. Two things made it hard to see: the manifest was identical either way, and all six tests added alongside the alias used `fixture()`. Fixed by `_rescuePreUpgradeOnDark()` and four new tests, two confirmed to fail without it.
- **Marking both names deprecated with a bare `@deprecated` tag.** Passed every check run — manifest field present, `cem-check` clean, editors rendering the strikethrough — so the criterion was recorded as met. Reading the generated `dist/index.d.ts` showed what consumers actually hover: `@deprecated true - DEPRECATED - use ...`. The migration guidance every consumer saw was the word `true`, directly undercutting the criterion it was meant to satisfy.
- **Believing the `shape`/`size` narrowing was a compile-surface change.** Documented across three sections of this file as the one thing an upgrading TypeScript consumer would have to act on, and weighed against a PATCH release. A `tsc --strict` probe disproved it. The claim had been reasoned from the manifest diff — real and correct — without checking whether the emitter's output could act on it.
- **Adding `@default 'rounded'` and `@default 'md'`.** Added on the assumption that the ternaries in `_initializeDefaults()` set them. They don't — that method runs before `type` is available, so both always evaluate to `null`. The observed defaults come from the inner `auro-button`. The tags reached `docs/api.md` as real defaults before being removed as inaccurate.
- **Retitling the commit to `docs:`.** Rejected after reading the shared release config, which gives unscoped `docs:` no release. The metadata work and the reflection fix were squashed into a single `fix:` commit; the `chore:` commit carrying the auro-cli 4.0.0 bump stayed separate and triggers no release.
