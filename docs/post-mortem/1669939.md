# AB#1669939

## Executive Summary

A link on a page can be set up to behave like a button, for example to open a dialog. The `auro-hyperlink` component handled this correctly the first time it appeared, but the next time anything about the link changed, such as switching it to the dark-background style, it quietly turned back into an ordinary link. It lost its button role and its place in the keyboard tab order, and clicking it followed the link's address instead of running the button's action. Screen reader and keyboard users were the most affected, and the problem was easy to miss.

This work makes the link keep its button behavior no matter how many times it is updated, and adds tests that catch the problem if it comes back. It also lets the component's documentation say when the `role` option applies.

Ticket: [AB#1669939](https://itsals.visualstudio.com/E_Retain_Content/_workitems/edit/1669939)

## The Problem

Setting `role="button"` on `auro-hyperlink` is how teams use a link as a button. It worked on first display and then stopped working as soon as the component updated. Because the page looked the same, nothing flagged it, and none of the existing tests updated a link that had this role.

## Root Cause

- `src/auro-hyperlink.js`: `renderLayoutDefault()` read `this.role` to decide the inner link's `role`, `tabindex`, `href` and `hyperlink--button` class.
- `firstUpdated()` calls `transportAllA11yAttributes`, which moves `role`, `tabindex` and `aria-*` from the host onto the inner `<a>` and removes them from the host (`removeOriginal` defaults to true). After that, `this.role` (the browser's reflection of the attribute) is `null`.
- Any later render therefore removed `role` and `tabindex`, dropped the button class and put an `href` back on the inner link. The link became a normal navigating link.
- No test re-rendered a `role="button"` link, so the suite stayed green.

## The Fix

- `src/auro-hyperlink.js`: added a private `linkRole` getter that returns `attributeWatcher?.getObservedAttribute("role") ?? this.role`, and made `renderLayoutDefault()` use it everywhere it used `this.role`. The first render falls back to `this.role`, because the watcher doesn't exist yet.
- `src/component-base.mjs`: declared `role` in `static get properties()` with its full description, `@relevantWhen type !== "cta"` and `@category behavior`. This replaced the class-level `@property` tag and its "needs to stay in this block" comment.
- `test/auro-hyperlink.test.js`: three new tests for a forced re-render, changing `appearance`, and a role set after the element upgrades.
- `docs/api.md`: regenerated, so `role` now appears as an attribute.

## Why This Works

- The transporter records the value it moved, and that record survives the host attribute being removed, so every render sees the same role.
- With the same role each time, Lit leaves the inner link's attributes unchanged on re-render.
- A role added after the element loads is moved by the transporter's observer, and the third test covers it.
- We confirmed the tests catch the bug: with the old behavior restored, the suite no longer completed, and with the fix it passes (70 of 70 tests). The build and strict manifest check are clean.

## Outcome

- A link with `role="button"` keeps its button role, tab stop and styling after any update.
- The component's documentation now states that `role` applies to standard and navigation links, not call-to-action links, in a structured field.
- The work is in the working tree and is not yet committed, reviewed or released.

## Ticket Completeness

3 of 3 acceptance checklist items are resolved in the working tree, but the work isn't committed or released, and part of the ticket's risk list is only partly covered.

**Resolved**
- **A `role="button"` link keeps its role, tab stop and button styling after a forced update and after another property changes.** Done through `linkRole`; covered by the first two new tests.
- **A role added after the element loads is applied to the inner link.** Covered by the third new test.
- **New or updated WTR tests for re-rendering a `role="button"` link are added and pass.** Three tests added; 70 of 70 pass.

**Not Resolved / Partial**
- **Checking links whose `role` is added, changed or removed after the first render.** Partial: adding is covered. Changing or removing a role after the transporter has moved it isn't detected, and the change doesn't address it.
- **Impact on `auro-popover`.** Not assessed; the ticket flagged it as a risk and it wasn't checked against that repo.
- **Reproduction on the docs site and on a real page.** Not done; the behavior was verified in the browser test runner only. The ticket records "unknown" for both.

## Learnings

- When a component moves attributes off its host, any render logic must read the moved value, not the host. Otherwise the second render quietly undoes the first.
- In this repo's test runner, a failing assertion on the re-rendered link showed up as "Browser tests did not finish within 120000ms", not as a normal failure. Treat that message as a possibly failing test.
- The old comment saying `role` "needs to stay in this block to avoid conflicts with the testing framework" was a symptom of this bug, not a real framework limit.
- A green suite proves only what it tests. A first fix attempt that passed all 67 tests had never been exercised by a re-render test.
- Structured `@relevantWhen` and `@category` work on properties declared in `properties()` and on slots, but not on `@cssprop` or class-level `@property` (see AB#1658021).
- Add a re-render test for any component that moves attributes after its first render.

## Iterations That Didn't Work

- Declaring `role` as a plain reactive property: tests failed (the runner reported a timeout), because the host attribute was cleared, the property fell back to `null` and re-rendered the link without its role.
- Declaring `role` with `attribute: false` and `noAccessor: true` just to carry the manifest tags: the suite stayed green and the tags worked, but the underlying bug was still there. The stricter re-render tests exposed it.
- Inline `{@relevantWhen}` tags in the class-level `role` description: not parsed into manifest fields and printed literally in the docs, so reverted.
